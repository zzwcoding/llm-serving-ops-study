# 0015 调参实验④:前缀缓存(阶段 3.4,Agent 开发者最该懂的一个)

## 三问(阶段动机)

```
✅ 3.1 砍上下文  ✅ 3.2 显存水位  ✅ 3.3 限并发  ✅ 3.4 前缀缓存(你在这里,Phase 3 收官)
```

- **这阶段干嘛的:** 对比两组请求——30 个各不相同的长 prompt vs 30 个共享同一段长开头的 prompt,看 TTFT 差距。
- **什么需求逼的:** 你的 Agent 应用,每个请求都带着同一份几千字的 system prompt(角色设定、工具说明)。如果每个请求都重算这段,白白烧钱烧时间。
- **解决了什么麻烦:** 前缀缓存让"相同的开头"只算一次。懂它,你的 prompt 设计习惯会直接变成省钱习惯。

## 全链路一览

```
30 个请求,开头都是同一段 500 token 的 system prompt
   │
   ▼
第 1 个请求:prefill 老老实实算完 500 token,顺手把 KV 存进"前缀缓存"
   │
   ▼
第 2~30 个请求:发现开头一模一样 → 直接复用缓存,跳过 500 token 的计算
   │
   ▼
Grafana:prefix_cache_hits_total 上涨,TTFT 明显低于第一组
```

类比:30 个人来复印同一份文件的前 10 页。第一个人复印完,
复印店把前 10 页的母版留下了;后面 29 个人直接从第 11 页开始——**前 10 页不重复印**。

## 跟着数据走

1. 服务不用改参数(这个版本前缀缓存默认开着,1.2 的启动日志里 `enable_prefix_caching=True`)
2. 跑 A 组:30 个请求,每个 prompt 都不同 → 记录 TTFT P99
3. 跑 B 组:30 个请求,共享同一段长 system prompt → 记录 TTFT P99
4. 对比两组 TTFT,并看 `vllm:prefix_cache_hits_total`(前缀缓存命中次数)的变化

## 新技术点四要素

**Prefix Caching(前缀缓存)**
- 名字:前缀缓存(Automatic Prefix Caching,APC),vLLM 内置功能
- 作用:不同请求的 prompt 开头如果逐字相同,这段的 KV 计算结果可以复用。KV 缓存从"一次一扔"变成"相同开头大家共用"
- 参数:`--enable-prefix-caching`(新版默认开);命中率看 `vllm:prefix_cache_hits_total` 和 `vllm:prefix_cache_queries_total`
- 用法:对调用方的要求只有一条——**把不变的内容(system prompt、工具定义)放在 prompt 最前面**,变化的内容放后面。顺序反了缓存就失效

## 关键顿悟

- **前缀缓存是"开头相同才生效"。** 中间相同没用,必须从第一个 token 起逐字一致——所以 prompt 模板里时间戳、随机 ID 千万别放开头。
- **Agent 场景的省钱王。** 固定 system prompt 越长,省得越多;这就是为什么"prompt 结构设计"是应用层的性能优化。
- **这是 1.5 课的闭环。** prefill 贵 → 相同前缀只 prefill 一次 → TTFT 和成本一起降。推理层的每个概念最后都会落到"你的应用怎么写"上。

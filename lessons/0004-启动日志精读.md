# 0004 启动日志精读(阶段 1.2,全程最重要的一课)

## 三问(阶段动机)

```
✅ 0.环境准备  ✅ 1.跑起服务  ✅ 1.2 读日志(你在这里)  ⬜ 1.3 调接口  ⬜ 2.监控  ⬜ 3.调参  ⬜ 4.压测  ⬜ 5.量化与K8s
```

- **这阶段干嘛的:** 把 vLLM 启动时刷屏的日志读懂——里面藏着这个服务的全部家底。
- **什么需求逼的:** 服务的"承载力"在启动那一刻就定死了,不看日志就是闭着眼睛运维。
- **解决了什么麻烦:** 以后任何 vLLM 服务,扫一眼启动日志就知道"能扛多少并发、显存够不够用"。

## 全链路一览

```
启动时 vLLM 做三件事:
1. 称体重:模型权重占多少显存(3 GB)
2. 量房子:总显存 24 GB,减去权重和杂项,剩下多少
3. 划车位:剩下的显存全划给 KV cache,算出能停多少"token"
   │
   ▼
得出结论:Maximum concurrency = 能同时接待多少个请求
```

## 跟着数据走(一道算术题,日志原话照抄)

```
Using max model len 32768                      ← 每个请求最长 3.2 万 token
Model loading took 2.98 GiB                    ← 权重占了 3 GB 显存
Available KV cache memory: 18.22 GiB           ← 剩下 18.22 GB 全给缓存
GPU KV cache size: 682,352 tokens              ← 这些缓存能装 68 万个 token
Maximum concurrency for 32768 tokens: 20.82x   ← 满长度请求能同时来 20 个
```

算一遍给你看:

```
24 GB 总显存
 − 3 GB 权重(1.5B 参数 × 2 字节,参数越多占越多)
 − ~2 GB 杂项(CUDA Graph 0.48 GB + 激活值 + 系统预留)
 = 18.22 GB → 划成 68 万个 token 的车位
 ÷ 32768(一个请求最长占 3.2 万个车位)
 = 20.82 → 满长请求最多同时 20 个
```

**如果实际对话平均只有 2000 token:** 682352 ÷ 2000 ≈ 341,能同时接待三百多个请求。所以——**并发能力不是固定数字,是"缓存总量 ÷ 你的请求实际长度"**。

## 新技术点四要素

**KV Cache(模型的"短期记忆")**
- 名字:Key-Value Cache,键值缓存,Transformer 注意力的副产物
- 作用:模型写每个字都要回头读前文。不缓存 = 每写一个字把整段对话重算一遍(慢到没法用);缓存 = 前文的"读书笔记"存在显存里随用随取。**代价:每个 token 都要占一个显存车位**(这个模型约 28KB/token;70B 大模型会贵好几倍)
- 参数:车位单价由模型结构定死(层数、宽度、精度);总车位数由剩余显存决定
- 用法:不用手管,vLLM 的 PagedAttention 自动划车位;**但你要会算"车位总数 ÷ 单请求长度 = 并发数"**

**CUDA Graph(计算"宏录制")**
- 名字:CUDA Graph
- 作用:把重复的计算步骤录成"宏",一键重放,省掉 CPU 反复下指令的开销。日志里那 0.48 GB 就是它占的
- 参数/用法:vLLM 自动处理,知道它存在、占一点显存即可

## 关键顿悟

- **显存预算公式:总显存 = 权重 + KV cache + 杂项。** 估算"这卡能不能跑这模型"就算这笔账。
- **KV cache 是大头,不是权重。** 3 GB 权重 vs 18 GB 缓存——服务能扛多少并发,几乎完全由缓存大小决定。
- **启动时一次性分完显存。** `gpu_memory_utilization=0.92`(默认用 92%)就是这个意思:先圈地再营业,运行中不再向系统要地——这是 vLLM 高吞吐的关键设计,也是 Phase 3 要调的参数。

# 0006 亲眼看 GPU 干活(阶段 1.4)

## 三问(阶段动机)

```
✅ 0.环境  ✅ 1.1 起服务  ✅ 1.2 读日志  ✅ 1.3 调接口  ✅ 1.4 盯显卡(你在这里)  ⬜ 1.5 prefill/decode  ⬜ 2.监控 ...
```

- **这阶段干嘛的:** 一边发请求,一边盯 `nvidia-smi`,把"推理 = 显存 + 计算"这句话从概念变成亲眼所见。
- **什么需求逼的:** 排障时要能看懂"服务忙不忙、瓶颈在哪",先要建立正常状态的手感。
- **解决了什么麻烦:** 理解一个反直觉现象——**干活的时候显存占用不动,只有利用率在跳**。

## 全链路一览

```
窗口1:vLLM 服务(日志滚动,别动它)
窗口2:nvidia-smi -l 1(每秒刷新的仪表盘)
窗口3:curl 发请求(发一个要求长回答的问题)
   │
   ▼
观察:请求发出的一瞬间,窗口2 的哪个数字动了?
```

## 跟着数据走

1. 窗口2 先敲 `nvidia-smi -l 1`,记录空闲基线:显存 ~22G(不变),利用率 0%
2. 窗口3 发一个"写一篇 500 字作文"的请求(让它生成久一点)
3. 盯窗口2:**利用率(GPU-Util)跳到几十甚至 90%+**,回答生成完又掉回 0%
4. 再看显存:**纹丝不动,还是 ~22G**

## 为什么显存不动?(本阶段唯一的新概念,承接 1.2)

回忆 1.2:vLLM 启动时就把 92% 显存圈走了(权重 + KV cache 车位全划好)。
干活时只是在**已经圈好的地里**搬数据、算矩阵,不再向系统新要显存。

类比:餐厅开业前把 100 张桌子全摆好了(显存已分配);客人来了就座、走了翻台
(请求进出),**桌子数量不变,变的是上座率(利用率)**。

判断服务状态就靠这两个数的组合:

| 显存 | 利用率 | 含义 |
|---|---|---|
| ~0 | 0% | 服务没起来 |
| 高 | 0% | 服务起来了,闲着(正常待机) |
| 高 | 波动 30~90% | 正常干活 |
| 高 | 持续 100% | 算力打满,请求在排队,该扩容了 |

## 关键顿悟

- **看显存判断"起没起",看利用率判断"忙不忙"。** 两个数各管一件事。
- **vLLM 是"先圈地再营业"。** 显存曲线平得像一条直线是健康的,不是异常。
- **`nvidia-smi -l 1` 是随身听诊器。** 以后做任何实验(调参、压测),旁边都开着它。
- **功耗和挡位也会说话。** 空闲 `P8 / 29W`(怠速),干活 `P2 / 71W+`(行驶挡),满载 `P0 / 逼近450W`。P 后数字越小挡位越高——看一眼功耗就知道卡有没有真在干活。

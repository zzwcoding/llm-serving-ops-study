# 0011 对照实验:让四条曲线跳起来(阶段 2.4)

## 三问(阶段动机)

```
✅ 2.1 裸看指标  ✅ 2.2 Prometheus  ✅ 2.3 Grafana  ✅ 2.4 对照实验(你在这里,Phase 2 收官)
```

- **这阶段干嘛的:** 给监控墙补齐 TTFT/TPOT/吞吐三条曲线,然后发一批并发请求,亲眼看四条曲线一起动。
- **什么需求逼的:** 空跑的监控没有感觉;亲手"制造流量 → 看曲线反应",指标才真正长在脑子里。
- **解决了什么麻烦:** 学会两个 PromQL 函数(`rate`、`histogram_quantile`)——这是从"抄指标名"到"会查账"的分水岭。

## 全链路一览

```
你写的压测脚本(窗口2:for 循环并发发 30 个请求)
   │
   ▼
vLLM(突然忙起来:排队、缓存占位、狂算)
   │  账本实时更新
   ▼
Prometheus(15 秒内抄到新账)
   │
   ▼
Grafana 四条曲线同时抬头:
  ① KV 缓存使用率 ↑   ② TTFT(P99)↑   ③ TPOT(P99)↑   ④ 吞吐 tokens/s ↑
```

## 跟着数据走(为什么四条线都要动)

30 个请求同时砸过来,每个要 400 token 的回答:

1. vLLM 的接待能力有限(continuous batching),一部分先算、一部分排队
2. 每个在算的请求都要占 KV 缓存车位 → **曲线①抬头**
3. 车多了路上挤 → 审题变慢(**TTFT↑**)、吐字变慢(**TPOT↑**)
4. 但整体吐字总量暴涨 → **吞吐曲线④冲到顶峰**
5. 请求做完 → 车位释放 → 曲线回落。**这一上一下,就是服务的"呼吸"**

## 新技术点四要素

**rate()(从里程表算车速)**
- 名字:PromQL 的 rate 函数
- 作用:`generation_tokens_total` 是里程表(只增不减的累计数),直接画出来是一条爬坡线,看不出"现在多快"。`rate(x[1m])` = 最近 1 分钟的平均增速,即"每秒吐多少 token"——**所有 counter 类型指标都要套 rate 才有意义**
- 参数:方括号里是时间窗口 `[1m]`;窗口越大曲线越平滑,越小越灵敏
- 用法:`rate(vllm:generation_tokens_total[1m])` → 输出吞吐(tokens/s)

**histogram_quantile()(从分桶算"最慢的那批")**
- 名字:PromQL 的分位数函数
- 作用:TTFT 是分桶记账(多少请求 <0.1s、<0.5s…)。这个函数反推出"P99 延迟"——**99% 的请求比它快,最慢的 1% 比它慢**。运维盯 P99 而不是平均值,因为平均值会被大量快请求"洗白",掩盖倒霉用户的真实体验
- 参数:0.99 = 看最慢 1%;`sum by (le)` 是固定搭配(把分桶合并后再算)
- 用法:`histogram_quantile(0.99, sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m])))`

## 关键顿悟

- **监控四件套:① 缓存水位 ② TTFT ③ TPOT ④ 吞吐。** 前两个管"会不会堵",后两个管"快不快"。
- **counter 套 rate,histogram 套 quantile。** 记住这两个搭配,PromQL 就入门了。
- **盯 P99 不盯平均。** 平均延迟漂亮不代表没人倒霉;P99 才是真实用户体验的底线。

# 0007 一次请求的两段旅程:prefill 与 decode(阶段 1.5)

## 三问(阶段动机)

```
✅ 0.环境  ✅ 1.1~1.4 服务跑通  ✅ 1.5 两段旅程(你在这里)  ⬜ 2.监控  ⬜ 3.调参  ⬜ 4.压测 ...
```

- **这阶段干嘛的:** 搞懂一个请求进入 vLLM 后经历的两个阶段——这是推理层最重要的概念,没有之一。
- **什么需求逼的:** 用户抱怨"卡"有两种完全不同的卡法:第一个字半天不出来 vs 后面吐字慢。病因不同、药方不同,必须分清。
- **解决了什么麻烦:** 看懂这两个阶段,监控指标(TTFT/TPOT)和调参方向你都能自己推出来。

## 全链路一览

```
你的请求(比如 36 个 token 的问题)
   │
   ▼
第一阶段:prefill(预填)——"审题"
   一口气读完整个问题,算出每个 token 的 KV 缓存
   产出:第一个回答 token
   │
   ▼
第二阶段:decode(解码)——"作答"
   逐字往外蹦:第1个字 → 第2个字 → ... → 第16个字
   每个新字都要用到 KV 缓存里存的前文
```

类比:考试时**通读题目**(prefill)和**动笔写答案**(decode)是两件事。
读题一目十行、一次读完(并行,快);写答案只能一个字一个字写(串行,慢)。

## 跟着数据走(拿 1.3 那次真实请求走一遍)

你问"用一句话解释什么是KV缓存"(36 tokens),模型答了 16 个 token:

1. **prefill**:36 个输入 token **并行**处理,一次算完 36 份 KV 缓存 → 蹦出第 1 个回答字
   - 从发请求到第 1 个字出来的等待时间 = **TTFT(Time To First Token,首 token 延迟)**
2. **decode**:循环 16 次,每次只算 1 个新 token(但要用到缓存里全部前文)
   - 相邻两个字之间的间隔 = **TPOT(Time Per Output Token,每 token 延迟)**
3. 总耗时 ≈ TTFT + 16 × TPOT

**关键差异:**

| | prefill(审题) | decode(作答) |
|---|---|---|
| 干活方式 | 一口气并行算所有输入 | 一次只能算 1 个 token,串行 |
| 吃什么资源 | 算力(矩阵狂算) | 显存带宽(反复读 KV 缓存) |
| 影响因素 | **问题越长,TTFT 越大** | **缓存越大,TPOT 越受影响** |
| 用户体验 | 第一个字等多久 | 吐字流不流畅 |

## 亲手感受(可观察实验)

发同一个请求两次,一次正常、一次开流式(`"stream": true`):

```bash
curl -N -s http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen2.5-1.5B-Instruct",
       "messages": [{"role": "user", "content": "讲一个200字的故事"}],
       "stream": true}'
```

(`-N` 关掉 curl 的缓冲,实时显示)你会亲眼看到:**等一小段(prefill)→ 第一个字出现(TTFT 结束)→ 后面一段段往外流(decode)**。这就是 ChatGPT 打字机效果的原理。

## 关键顿悟

- **"卡"要分两种。** 首字慢 = prefill 慢(输入太长/机器忙);吐字慢 = decode 慢(带宽/并发挤)。Phase 2 监控就是分别盯这两个数。
- **KV cache 是两段旅程的桥。** prefill 写入它,decode 反复读它——1.2 学的缓存,在这里闭环了。
- **长 prompt 贵得有道理。** 10000 token 的系统提示词,意味着每次请求 prefill 都要先"审"一万字的题——这就是 Agent 应用里 prompt 设计的成本来源。

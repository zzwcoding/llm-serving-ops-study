# 0012 调参实验①:砍上下文长度(阶段 3.1)

## 三问(阶段动机)

```
✅ 1.服务跑通  ✅ 2.监控  ✅ 3.1 max-model-len(你在这里)  ⬜ 3.2 显存水位  ⬜ 3.3 限并发  ⬜ 3.4 前缀缓存
```

- **这阶段干嘛的:** 把模型允许的最大上下文从 32768 砍到 4096,重启服务,看启动日志里"最大并发"怎么变。
- **什么需求逼的:** 你的 Agent 场景大部分对话就几百上千 token,32K 的"满长请求预算"纯属浪费——并发单价按最长的算,天花板就被拉低了。
- **解决了什么麻烦:** 同样的显卡,砍掉用不上的上下文,**并发承载力直接翻好几倍**,零成本。

## 全链路一览

```
--max-model-len 4096(每个请求最多占 4096 个车位)
   │
   ▼
KV 缓存总车位不变:682,352 个(显存没动)
   │
   ▼
启动日志:Maximum concurrency = 682352 ÷ 4096 ≈ 166x
(原来:÷ 32768 ≈ 20.8x)
```

类比:停车场总车位固定。原来按"每辆车都是 40 米长大货车"规划(32768),只能停 20 辆;
改按"都是家用轿车"规划(4096),能停 166 辆。**车还是那么多车,规划假设变了。**

## 跟着数据走

1. 窗口1 里 Ctrl+C 停掉 vLLM(学会正常停服务:Ctrl+C 是发 SIGTERM,让它优雅退出)
2. 加参数重启:`--max-model-len 4096`
3. 在新启动日志里找两行:
   - `Using max model len 4096`(上限变了)
   - `Maximum concurrency for 4096 tokens per request: 166.x`(并发暴涨)
4. 注意:KV cache 总量(682,352 tokens)和显存占用**不变**——我们只改了"单价假设"

## 新技术点四要素

**--max-model-len(上下文长度上限)**
- 名字:vLLM 启动参数,单位 token
- 作用:给"单个请求最长能占多少 KV 缓存"设天花板。它是 vLLM 算"最大并发"时的除数
- 参数:默认取模型自身的最大值(这个模型是 32768);调小 = 限制长文请求(超长会直接报错 400),换并发能力
- 用法:本项目挂载点——`vllm serve Qwen/Qwen2.5-1.5B-Instruct --max-model-len 4096`

## 关键顿悟

- **并发承载力 = KV 总缓存 ÷ 单请求预算。** 砍预算和加显存,效果一样,但砍预算不要钱。
- **上限是按业务定的,不是按模型定的。** 你的应用最长对话多少 token,就设多少(再留点余量);设大了是白白给并发能力打折。
- **调参 = 改假设。** 这类参数不改模型、不改代码,只改"对流量的预期"——理解业务比理解引擎更重要。
